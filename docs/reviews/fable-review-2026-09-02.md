# Fable review, 2026-09-02

Independent red-team review of the repository. No prior context with the project. Everything below was read or run today. `npm test` from the repository root passes: 41 tests in `packages/core/test`, 11 in `apps/vega-player/test-node`, 52 total, 0 failures, ~0.6 s.

## 1. Verdict

### (a) The hackathon submission plan: CONDITIONAL GO

The engineering is real and the measurement discipline is better than most hackathon entries will manage: every number in `docs/sync-report.md` reproduced exactly when I re-ran `npm run sync-report` against the committed device logs, and the unscripted Measurement R figures (n=48, p50 3 ms, p95 7 ms, max 68 ms) reproduced when I re-derived them from `docs/device-log-2026-09-02-render-latency.txt` by hand. That is the strongest single asset in the repository. What holds the verdict back is that the entire critical path to a submission is external and none of it has started: no product name approved (`docs/name-review.md` still says "awaiting Samuel's approval"), no `LICENSE` file anywhere in the tree, no DHH participant recruited (`docs/validation-plan.md` "Outreach has not been sent"), no physical Fire TV, no demo video, and the repository is private with a public URL listed as `[public URL after naming approval]` in `docs/devpost-draft.md`. Two of those are hard blockers rather than schedule risks. First, `apps/vega-player/src/w3cmedia/shakaplayer/ShakaPlayer.ts:1-13` carries an "AMAZON PROPRIETARY/CONFIDENTIAL" header instructing the reader to comply with "the accompanying LICENSE.TXT file", and no such file exists in this repository; that file is committed (`git ls-files` confirms it, along with `dist/shaka-player.compiled.js`) and the project intends to enter the Open Source mini-challenge with this tree. Second, five Roboto Flex TTFs are committed at `apps/vega-player/assets/fonts/` with no OFL text beside them, sourced per `docs/prior-art.md:57` from the Caption with Intention download whose PDF the same file describes as "All Rights Reserved". Publishing as-is is the single most likely way to lose points with a judge who opens the repository. The deadline (2026-10-23, internal 2026-10-15) leaves seven weeks, which is enough time, so the verdict is conditional rather than negative. Conditions: settle the Shaka redistribution question or switch to hls.js; ship OFL.txt with the fonts or drop them; add a LICENSE; send the study outreach this week; and correct the ten factual errors in README listed in section 2 before anyone outside the project reads it.

### (b) That this is a credible implementation of the Caption with Intention design system on Fire TV: CONDITIONAL GO

It is credible as a first software implementation and the captures prove it runs on the platform against real footage: the CI palette is in `apps/vega-player/src/theme.ts:20-31` verbatim, read-ahead white at 90% is in `DetailedOverlay.tsx:40`, the 90% box in `:101`, the lower-20% work area in `:19-23`, italic for off-camera in `:146`, the ♫ rule in `:167,175`, the word pop (25% lift, 1.15 scale) in `:81-82`, and `docs/captures/2026-09-02-native-words-thom-c003.png` shows word-by-word colour reveal drawn by the platform's own caption renderer, which is a genuinely novel result and the best thing in the build. It is not yet what `docs/prior-art.md:5` calls "implemented to the letter", and three of CI's four devices are compromised in the shipped code. Font size does not follow volume per word: `DetailedOverlay.tsx:127` computes one `lineSize` per cue and `:190` passes that same constant to every `WordEl`, so the per-word `loud`/`loudDb` in schema 0.2 changes nothing on screen, contradicting `docs/expressive-plan.md:84` and `README.md:257`. Weight does not follow pitch: `DetailedOverlay.tsx:36-37` sets both `fontWeight` and a family name, and FL-024 (`docs/friction-log.md:192-198`) records that the platform selects faces by family name and not by `fontWeight`, so what actually varies is width (Wide/Narrow), not weight — the claim in `docs/phase-reports.md:94,99` and integration row 34 overstates what the platform does. And the box does not cover its own text: `docs/captures/2026-09-02-ci-detailed-thom-bottom-two-lines.png` shows the second line rendered outside the black box, and `docs/captures/2026-09-02-sounds01-music-overlap-sidelane.png` shows a side-lane line clipped by the bottom of its box — both are cited as evidence that the box rule is Verified. Above all, the "verified" gate that distinguishes this from an automated effect is not doing what the documents say: every word, delivery and sound entry in the three real scenes was marked `verified` by machine (section 5). Fix those four and the claim is fully defensible; today it is a strong prototype oversold by one notch.

## 3. Correctness risks in the code

Ordered roughly by severity.

**3.1 The verification gate fails open on words and delivery.** `packages/core/src/resolver.ts:196` reads `if ((w.status ?? "verified") !== "verified")`; `:216` reads `if (!verified || (d.status ?? "verified") !== "verified")`. `packages/core/src/schema.ts:128` and `:141` both make `status` optional with no default. So a `words[]` entry or a `delivery` object with the field simply absent is rendered as verified. `apps/vega-player/src/screens/PlayerScreen.tsx:42-63` fetches `companion.en.json` over plain HTTP from a publisher URL and hands the parsed object straight to the controller. The one principle the whole product is built on — "only `verified` reaches the viewer" — is defaulted to `true`. It should be `(w.status ?? "proposed")`, or `status` should be required in the schema. No test covers the missing-status case; `tools/sync-report.ts:35` repeats the same default.

**3.2 Machine-invented spellings can reach the screen with no human in the loop.** `tools/author/delivery.py:75-79` synthesises a stretched spelling by repeating the last vowel group ("No" → "Nooo"). `tools/author/propose.py:45-47` merges delivery fields into word entries with `w.update(wd)`, and `:30` may already have set those entries to `status: verified` by alignment score. `resolver.ts:200-201` then renders `w.stretch` as the display token. That is a path from an audio measurement to a changed on-screen word with no editor. `README.md:109` says "an enhancement may disappear; the canonical caption may not"; a stretched spelling is the one enhancement that changes what the viewer reads. No shipped asset currently carries a `stretch` (I checked all eight companion files), so this has not fired, but nothing prevents it.

**3.3 `NATIVE_LEAD_MS` shifts every native caption 120 ms early on the strength of a measurement the project says overstates the lag.** `CaptionController.ts:42,156` subtracts 120 ms from every native cue's start and end. The calibration is Method A, and `README.md:187` says of Method A: "every error is late and clusters near the `timeupdate` granularity, which is undocumented, so the true render latency is probably smaller than the sampled media time suggests. This method cannot show it." If the true render latency is, say, 40 ms, the compensation now puts captions 80 ms *ahead* of the audio. Early captions on narrative video reveal a line before it is spoken; that is a worse failure than a late caption and the project has no measurement that can detect it (Measurement C is not done). The default should be 0 until a frame-accurate measurement exists, or the lead should be capped well below the observed median.

**3.4 The "nearest boundary" rule in the sync tool biases the headline number toward zero.** `tools/sync-report.ts:74` picks the candidate boundary closest to the sampled media time. Cue boundaries are seconds apart, so this is harmless at cue level. Word segments are 100-400 ms apart (see the c003 timings: 9181, 9483, 9603, 9784, 10307, 10408 ms) and the post-compensation errors span -115 to +122 ms, so an event can be attributed to the wrong word boundary and scored as a small error. The +16 ms p50 in `docs/sync-report.md:56` and integration row 35 is the number most likely to be wrong, and it is the number the project is proudest of.

**3.5 Forced alignment pairs words positionally and fails silently.** `tools/author/align.py:57-63` builds a flat list of WhisperX output words and a flat list of canonical tokens and zips them. `:59-60` prints a stderr warning if the lengths differ and continues "pairing by order up to the shorter list". One dropped or added word shifts every later token's timing by one for the rest of the scene. `:69-70` then clamps each timing into its own cue, so a shifted result looks plausible rather than obviously broken. Combined with `propose.py:30`'s score-based auto-verification, corrupted timings can be written as `verified` and shipped. There is no per-cue check that the aligner returned exactly as many words as the cue has tokens.

**3.6 `propose.py` marks delivery verified with no score test at all.** `tools/author/propose.py:44`: `cue["delivery"] = {**d, "status": "verified" if accept is not None else "proposed"}`. The `--accept-min-score` flag is documented (`:8-10`) as gating *word alignment* scores. Passing it silently verifies every cue's `delivery` object, which is what drives on-screen font size. All 11 tos-bridge cues, all 19 tos-lab cues and all 31 Envelope cues have `delivery.status: "verified"` on this basis.

**3.7 A code comment asserts a safety property the code does not have.** `tools/author/propose.py:51-52`: "Protected regions are honoured by the resolver only for verified cues, so a wrong face box can hide nothing." `resolver.ts:324` applies `ctx.protectedRegions` to every cue with a side-lane candidate regardless of its status, and `ShotDef` has no `status` field at all in `types.ts:49-54` or `schema.ts:53-80`. A wrong machine-proposed face box does change placement. `assets/tos-bridge/companion.en.json` shot `s16` carries an unreviewed YuNet rectangle of 0.349 × 0.552 — a third of the frame — for six seconds.

**3.8 Untimed and unverified words are inferred as "spoken" and take the speaker colour.** Two places do this independently: `resolver.ts:432` (`for (const w of timed) if (w.startMs <= t && w.i > spokenUpTo) spokenUpTo = w.i`) colours every token up to the highest started index, including tokens whose entry was dropped as unverified; `DetailedOverlay.tsx:141-145` `inferredSpoken` does the same for the overlay. It is presentation, not text, but the verified state of a word is being inferred from its neighbours and then shown to the viewer as if it were data. `resolver.ts:431` goes further: with no verified timings at all, `spokenUpTo = tokenCount - 1` colours the entire cue.

**3.9 Token indices are computed from two different strings.** `resolver.ts:190` and `:283` and `schema.ts:309,373` index `visibleTokens(cue.rawText)`, which runs `normalizeVisibleText` (`normalize.ts:42-47`): strip tags, `decodeEntities` (all numeric and eight named entities, `normalize.ts:15-33`), NFC, collapse whitespace. `DetailedOverlay.tsx:132` indexes `c.text.split("\n").map(l => l.split(/\s+/))` where `c.text` is `plainText`, produced by `vtt.ts:63-67`, which decodes only `&lt;`, `&gt;`, `&amp;`. A cue containing `&nbsp;`, `&#39;` or any other entity produces different token counts on the two paths, so the wrong word is coloured, capitalised or emphasised. `resolver.ts:283` compounds it by indexing a third string (`c.text.split(/\s+/)`, which yields a leading empty element when the text starts with whitespace).

**3.10 `rebuild()` can leave orphan cues on the native track and can throw out of the constructor.** `CaptionController.ts:168-170`: the `removeCue` loop is individually try/caught, the `addCue` loop is not, and `this.nativeCues = next` is assigned only after both loops. If `addCue` throws partway, the already-added cues are not recorded and the next rebuild cannot remove them, so the track accumulates duplicates. `rebuild()` is called from the constructor at `:114`, so any throw inside it (including from `nativeWordSegments`, which is outside the per-cue try/catch that protects `resolveTrack`) propagates to `PlayerScreen.tsx:134`, is caught at `:144`, and the viewer gets "The player could not start." — video and Standard captions both gone. `README.md:106` promises "a malformed companion file leaves video and Standard captions intact".

**3.11 `dispose()` does not detach cues.** `CaptionController.ts:245` clears `oncuechange` and listeners but leaves `this.nativeCues` on the shared `TextTrack`. It happens to be safe today only because `PlayerScreen.tsx:154` deinitialises the whole `VideoPlayer` in the same cleanup.

**3.12 A mode change during asset load is silently dropped.** `PlayerScreen.tsx:107` captures `settings` in the async IIFE closure; the controller is constructed at `:134-137` after an `await` that can take up to 2.5 s (`:54`). The effect at `:160` that pushes viewer preferences into the controller runs on `settings.mode` changes; if the viewer changes mode during the load, that effect fires with `controllerRef.current === null`, the change is lost, and the controller is then built from the stale closure value. The effect will not re-fire because the dependency did not change again.

**3.13 State is mutated inside an argument expression.** `CaptionController.ts:217` assigns `this.state = { ...this.state, sfxStart }` inside `layoutNow`, which is called as an argument to `this.emit(...)` at `:174`, `:194`, `:229` and `:239`. It works only because JavaScript evaluates the argument before the call and `emit` (`:118`) spreads `this.state`. Any reordering breaks sound-event timing silently.

**3.14 Five of six main speakers can get native word colouring; one cannot, silently.** `CaptionController.ts:71-79` `nativeColorClass` returns `undefined` for `speaker-4` (CI Main Orange) and for all twelve `support-*` tokens, because WebVTT has no standard class for them. `:162` then returns a single un-split cue. A speaker assigned `speaker-4` gets no colour *and* no word-by-word reveal on the native path, with no `fallbackReasons` entry recorded anywhere. The unit test at `controller.test.ts:79-83` documents the colour gap but not the silent loss of word colouring.

**3.15 The word reveal disappears entirely when the viewer sets a caption colour, with no fallback reason.** `DetailedOverlay.tsx:189`: `color={viewerTextColor ?? speakerColor} readAhead={viewerTextColor ?? READ_AHEAD}`. When the viewer has chosen a text colour, both are the same value, so every word renders identically at every moment. That is the correct precedence (`docs/accessibility-decisions.md:27`) but the feature vanishes with nothing logged and nothing in the diagnostics panel to explain it.

**3.16 Dead code that makes diagnostics lie.** `resolver.ts:133-134`: `if (!verified) base.fallbackReasons.push("speaker_unavailable"); base.fallbackReasons = base.fallbackReasons.filter(r => r !== "speaker_unavailable");` — the push is unconditionally undone on the next line, so `speaker_unavailable` can never appear in a log even though it is a declared `FallbackReason` (`types.ts:182`). `tools/sync-report.ts:54` has a similar dead branch (`m.group ? m.group(1) : m[1]`; `RegExpExecArray` has `groups`, not `group`).

**3.17 `layoutActiveSet` pushes a reason after de-duplication.** `resolver.ts:337` builds `fallbackReasons: Array.from(new Set(reasons))`, then `:339` pushes `"no_safe_lane"` onto the already-deduplicated array, so it can appear twice.

**3.18 `resolveAlone` groups by pairwise overlap, not transitive closure, and does not share occupancy across groups.** `resolver.ts:385`: `eligible.filter(o => o.startMs < c.endMs && c.startMs < o.endMs)`. Cue A overlapping B and B overlapping C (A and C disjoint) are laid out in two separate groups with independent `occupied` arrays (`:303`), so A and C can be assigned boxes that overlap a third cue placed in the other pass. This is the native path used for Standard and Speaker-aware, i.e. the default mode.

**3.19 Seeking with an unknown duration seeks to a negative time.** `PlayerScreen.tsx:188` and `:190`: `p.currentTime = Math.min((p.duration || 0) - 0.3, ...)`. If `duration` is `0` or `NaN` (the MSE path is still loading), this sets `currentTime = -0.3`.

**3.20 Development-only code ships in the viewer path.** `PlayerScreen.tsx:192-199` maps Page Up / Page Down to `requestCaptionTextSize` plus an in-app simulated caption size, with no `__DEV__` guard; a viewer pressing Page Up on the remote gets `very_large` simulated captions. `PlayerScreen.tsx:225-228` renders two off-screen font-probe `<Text>` elements on every frame of the player screen. FL-008's own lesson (`docs/friction-log.md:83`) is "keep the player screen free of per-frame state updates".

**3.21 No offline path.** `apps/vega-player/src/media/config.ts:17` hard-codes `DEV_HOST = "http://192.168.1.84:8081"`, and every scene (including both Tears of Steel excerpts) resolves its HLS URI, and for the film scenes its caption and companion URIs, against it. FL-008's side finding (`docs/friction-log.md:82`) records that packaged assets are readable at `file:///pkg/assets/raw/`, and the app never uses it. The demo depends on a laptop running `http-server` on the same LAN — with FL-018 (the VVD exiting after four hours) and FL-005 (no recording command, VVD may crash under recording) also in play on capture day.

**3.22 The publisher path pairs a remote track with a bundled companion.** `PlayerScreen.tsx:59`: `companion: companion ?? bundledCompanion`. If the publisher serves a newer VTT and no companion, the app validates a stale companion against fresh text. The hash check catches it cue by cue, so it degrades safely, but the design intent should be explicit: either take both from the same source or neither.

**3.23 The `▶` / `◀` direction markers render with emoji presentation.** `DetailedOverlay.tsx:156,168,174` emit U+25B6 and U+25C0. In `docs/captures/2026-09-02-sounds06-technician-machinery.png` the marker renders as a coloured orange glyph, not white type. CI's rule (`docs/prior-art.md:27`) is that sound effects are white. Use a text-presentation variation selector or draw the arrow.

**3.24 Window dimensions are read once at module load.** `theme.ts:40` calls `Dimensions.get("window")` at import time and every size, including `windowSize.height` which drives caption size in `DetailedOverlay.tsx:98,127`, derives from it. FL-021 documents that the VVD window size matters.

## 4. Accessibility and design risks

**4.1 The palette breaks the project's own contrast target.** `docs/accessibility-decisions.md:85` sets "at least 4.5:1 text-to-background contrast wherever the app controls the colours (WCAG 1.4.3)" and `:87` says contrast "has been checked by inspection … not measured". Measured: CI Main Red `#E51717` (`theme.ts:23`, token `speaker-3`) is **4.47:1** against pure black and **4.13:1** against the 90%-opaque box over mid-grey video. It fails. `speaker-3` is assigned to `technician` in `assets/tos-bridge/companion.en.json` and to `amara` in The Envelope, and it is in a shipped capture (`2026-09-02-envelope-words-amara-red.png`). CI Main Pink `#E517E5` is 5.59:1 and CI Main Orange `#E58017` is 7.43:1 — both pass, but the box is 90% opaque, not 100%, so all of these drift with the picture behind them. Four of the twelve support shades (`support-8`, `support-9`, and by inspection the darker end) sit in the 5-6:1 band and will fail over a bright shot. Adopting CI's palette verbatim imported a contrast problem that CI does not have to solve, because CI is burned into a finished picture by an editor who can see the result.

**4.2 The read-ahead state and the unverified-word state are the same white.** `DetailedOverlay.tsx:137` sets `baseColor` to `READ_AHEAD` (white 90%) for not-yet-spoken words; `:189` passes the same `READ_AHEAD` to `WordEl`. A word whose metadata was rejected also renders in that white. So does a sound effect (`:137`, `isSound` branch). Three semantically different states share one appearance and a viewer cannot distinguish "not said yet" from "we could not verify this". `docs/captures/2026-09-02-ci-detailed-thom-unverified-word.png` is the proof: "I'm **not** freaked **out by-** it's..." with cyan on tokens 1, 3, 4 and white on 0, 2, 5 produces a pattern that reads as arbitrary emphasis. `assets/tos-bridge/companion.en.json` c003 shows the mechanism — tokens 6, 7, 8 ("just", "want", "to") are `proposed` while 0-5 and 9-12 are `verified`, so in `docs/captures/2026-09-02-ci-detailed-thom-bottom-two-lines.png` the reveal reads backwards: "just want to" is white while the later "be awesome in space." is cyan. For a DHH viewer using colour as the attribution cue, an unreliable colour is worse than no colour. Either colour unverified words the same as verified ones (the `inferredSpoken` path already does this, inconsistently) or hold the whole cue at cue-level colour until every word is verified.

**4.3 A cue can end up with neither a label nor a lane, leaving colour as the only attribution cue — which section 4 of `accessibility-decisions.md` forbids.** `docs/accessibility-decisions.md:32-36`: "A speaker is never identified by colour alone … only in addition to a text label and a stable lane." Line 1 of `docs/device-log-2026-09-02-render-latency.txt` shows exactly that state on a real run: `c003:bottom_center!label_suppressed_by_rule|words_unverified|size_rejected|no_safe_lane`. The label was suppressed by the frequency rule (`labels.ts:64`, same-speaker run), the side lane was rejected on size (`resolver.ts:322`), so the cue is at bottom_center with no label — and in Detailed it still carries the speaker colour (`resolver.ts:160`, unaffected by lane loss). The rule needs an enforcement point: if `lane === "bottom_center"` and `speakerLabel` is undefined, either force the label on or drop the colour. `layoutActiveSet:348-355` already does exactly this for the two-cue bottom-stack case; it does not do it for the single-cue case.

**4.4 The fair-baseline gate fails on the project's own new check.** `docs/accessibility-decisions.md:101` commits to "reading speed at or under 20 characters per second" as an explicit gate (G6) before any claim is made, on the grounds that "if the comparison is not fair, nothing the study finds is worth reporting". The reading-rate warning added in commit 797d942 now reports **12 of 31** Envelope cues and **6 of 11** tos-bridge cues over 180 wpm, with tos-bridge c008 at 420 wpm (7 words in 1.00 s) and c004 at 244 wpm. These are the pilot instrument and the demo. A Standard baseline that is too fast to read makes the enhanced modes look better for the wrong reason — the exact bias the fairness rule exists to prevent. Re-time both tracks before the pilot, and make the reading-rate check an error rather than a warning for non-fixture scenes in `tools/bundle-assets.ts`.

**4.5 `accessibility-decisions.md` contradicts itself inside one file.** Section 6, line 47: "Word-by-word reveal is not implemented. It is the highest-motion feature and the least supported by evidence for narrative video, so it was the first thing cut." The addendum at line 140 of the same file describes the word pop as implemented. This is the project's accessibility record; a judge or a participant reading it finds a document that states a safety decision and then documents shipping the thing it ruled out, with no note that the decision was revisited or why. `docs/expressive-plan.md:36-38` does contain the reasoning for reversing it; section 6 needs to point at that reversal, not sit unchanged. Section 5's "The four speaker tokens in `apps/vega-player/src/theme.ts`" is also stale — there are 19.

**4.6 Pitch bands encode voice pitch rather than delivery, and the per-speaker normalisation is computed and thrown away.** `docs/expressive-plan.md:57` specifies "fundamental frequency (pyin) relative to that speaker's median". `tools/author/delivery.py:60-62` computes `spk_med`, per-speaker pitch medians in the semitone domain, and `:73` then uses absolute bands: `-1 if fmed < 160 else 1 if fmed > 200 else 0`. `spk_med` is never read. Adult female speaking f0 typically sits at 165-255 Hz and adult male at 85-180 Hz, so in practice the "pitch band" reduces to the speaker's sex, and `DetailedOverlay.tsx:37` then renders that as a permanently narrower or wider typeface for that character. That is not what CI's rule is for and it is not what the plan says the tool does. Either use the per-speaker median that is already computed, or state plainly in the docs that the width axis carries absolute voice pitch.

**4.7 Nothing prevents a caption from overflowing the CI work area.** `DetailedOverlay.tsx:127` computes `lineSize = windowSize.height * heightPctForLoudness(...) * scale`, where `heightPctForLoudness` can return 0.12 (`resolver.ts:269`) and `SIZE_SCALE` can be 2.0 at `very_large` (`:25`). One line can therefore be 24% of the screen height; two lines, 48%. The bottom lane is fixed at `bottom: "7.5%"` (`:20`) with no height clamp and no two-line cap, and `resolver.ts:319` breaks out of the lane loop at `bottom_center` without ever running the size, title-safe or protected-region checks on it. `docs/accessibility-decisions.md:127` claims "No caption may overflow the viewport or sit over a known protected region". For the bottom lane in Detailed at a large system size with a shouted cue, nothing enforces that. CI's own "at most two lines on screen" (`docs/prior-art.md:25`) is also not enforced anywhere.

**4.8 The black box does not reliably cover its own text.** `docs/captures/2026-09-02-ci-detailed-thom-bottom-two-lines.png`: the box ends after line 1 and "just want to be awesome in space." sits over the picture with no backing. `docs/captures/2026-09-02-sounds01-music-overlap-sidelane.png`: the side-lane line "Whatever, Thom. We're done." is clipped by the bottom edge of its box, with the lower half of the glyphs outside it. The likely mechanism is `styles.wordRow` at `DetailedOverlay.tsx:219` — `{ flexDirection: "row", flexWrap: "wrap", alignItems: "baseline" }` — under-measuring its height when children are `Animated.Text` carrying a `transform`. Whatever the cause, this is the one CI rule that exists purely for legibility (CI 2.4.1, 90% black), it is claimed Verified in integration row 28, and two of the cited captures show it broken.

**4.9 The native renderer's actual placement is not where the estimator thinks it is.** `docs/captures/2026-09-02-native-words-thom-c003.png` shows a bottom-lane native cue (`line: 90`, `lanes.ts:38`) drawn across the middle of the frame over both actors' torsos. `lanes.ts:80` models `line%` as anchoring the box *bottom*; per WebVTT with `snapToLines: false` the default `lineAlign` is `start`, which anchors the *top*. Whichever the platform does, the estimator's boxes are not the boxes the renderer draws, which means the title-safe check (`lanes.ts:93-100`), the protected-region check (`resolver.ts:324`) and the collision check (`:325`) are all being evaluated against rectangles that do not correspond to what appears on screen. `docs/prior-art.md:79` names covering the speaker's face as "the most cited failure"; the protected-region machinery exists to prevent it, and on the native path it is currently protecting a rectangle that is in the wrong place.

**4.10 The off-screen/italic decision is made by regex over a display label.** `resolver.ts:145`: `offScreen = /UNKNOWN|VOICE|PHONE|RADIO|OUTSIDE|OFF[- ]SCREEN/i.test(labelText) || !at.revealed || speakerDef.offScreen === true`. A character whose label happens to contain "VOICE" is rendered italic and treated as not visually identifiable. `SpeakerDef.offScreen` already exists (`types.ts:44`) as the explicit signal; the string match should be deleted.

**4.11 Where the research is used past what it supports.** `docs/prior-art.md:77` cites a 300 ms drop-off figure, a "2022 industry survey", a KU Leuven claim about a 100 ms threshold and a "50 ms imperceptible" figure, and then says at `:82` "The sync figures are industry reports rather than peer-reviewed thresholds and are used as direction, not as claims." They were used to justify `NATIVE_LEAD_MS = 120`, which changes what every viewer sees on every cue in two of three modes. That is a claim. Everything else in section 3 of `prior-art.md` is used carefully: Caption Royale (`:38`) is reported with its inconvenient finding intact ("All styled captions scored lower than baseline on ease of reading"), and the toggles in `SettingsPanel.tsx:32-33` are the right response to it. The one place to tighten is that `store.ts:29` defaults both new toggles to `true`, so a viewer who selects Detailed gets colour, size and weight all at once — which is the condition Caption Royale found hardest to read. Consider defaulting `deliveryTypography` to off until the pilot says otherwise.

**4.12 Nothing in the overlay is tested.** All 41 core tests exercise `packages/core`; the 11 app tests exercise `CaptionController` and the older `captionRuntime`. `DetailedOverlay.tsx` — where every Caption with Intention rule, every contrast decision, the box, the sizing, the italic rule and the pop live — has zero automated coverage. That is where four of the findings in this section are.

## 5. Process and evidence hygiene

**5.1 Reproducibility is genuinely good, and that is the project's best defence.** Every table in `docs/sync-report.md` regenerated identically from the committed logs with `npm run sync-report`, and Measurement R regenerated identically by hand. The device logs are raw journald output, not summaries, so a sceptic can re-derive the numbers. `assets/fixture-*` scenes are selectable in the app so a reviewer can reproduce five integration rows on any device in a minute each (`docs/integration-tests.md:45`) — that is a strong and unusual move. The two gaps: Measurement R has no tool (`tools/sync-report.ts` does not parse `[render]` lines), and the lane calibration constants in `lanes.ts:67-68` have no recorded measurement anywhere.

**5.2 The "verified" data in every shipped scene was verified by machine, not by a person, and the demo assets are the ones `docs/authoring.md` explicitly says must not be produced this way.** `docs/authoring.md:23`: "On the development bench `--accept-min-score 0.5` marks well-aligned words verified and says so in `provenance`; **never use that for pilot or demo assets**." What is committed:

| Scene | Cues | Word entries `verified` | Cue-level `delivery` `verified` | Sound events `verified` | Cue `provenance` |
|---|---|---|---|---|---|
| `assets/tos-bridge` (the demo) | 9 verified / 2 proposed | 48 of 76 | 11 of 11 | 3 of 3 | all: `human_editor; words: whisperx auto-accepted (score>=0.5); pending human review` |
| `assets/tos-lab` | 0 verified / 19 proposed | 51 of 78 | 19 of 19 | 0 of 15 | same |
| `assets/the-envelope` (the pilot instrument) | 30 verified / 1 proposed | 117 of 134 | 31 of 31 | n/a | same, plus one `automated_suggestion` |

The three tos-bridge sound events carry `provenance: "panns-cnn14 score=0.89; label and status set on the dev bench, pending pilot review"` and status `verified`. Every `delivery` object in every scene is `verified` because `propose.py:44` sets it whenever `--accept-min-score` is present, with no score test. So the sentence that separates this product from an automated effects generator — "Only human-verified metadata reaches an enhanced render" (`docs/accessibility-decisions.md:123`) — is not true of any asset in the repository. **The provenance strings are honest, and that is to the project's credit**: the file itself says "pending human review". But the runtime does not read provenance, the documents do not qualify the claim, and every "Verified" row in `docs/integration-tests.md` from 28 to 37 was captured against machine-verified data. This is the finding most likely to unravel the project if a judge or a reviewer opens `assets/tos-bridge/companion.en.json`. It is also the cheapest to fix: a review pass in `tools/author/review_server.py` on eleven cues of tos-bridge, and honest `proposed` status everywhere else.

**5.3 The Envelope's delivery data measures a text-to-speech voice.** `docs/phase-reports.md:72`: "Footage is synthesized (macOS `say` voices over a stage graphic)." Its 134 word timings, 134 loudness measurements and 31 pitch/pace measurements were extracted by WhisperX and librosa from that synthesised audio, marked `verified`, and are what the Detailed-mode captures of The Envelope show. Nothing in `README.md` or `docs/integration-tests.md` says the delivery typography in those captures is derived from a TTS voice reading a script.

**5.4 Provenance in general is honest; the summaries are not.** The friction log is unusually good: FL-008 root-causes URL-mode failure with a control experiment on the unmodified official sample, FL-021 retracts a wrong hypothesis and reports the 90 minutes it cost, FL-023 documents a real renderer bug with a measured character-count shortfall. `docs/expressive-plan.md:3` opens by saying the previous plan was written before reading the Caption with Intention system. That kind of self-correction is worth more than the polish. What undermines it is that the summary documents drifted: ten factual errors in README (section 2), a self-contradiction in `accessibility-decisions.md`, two scene READMEs saying "schema 0.1" over 0.2 files, and an evidence path in `phase-reports.md:140` that matches no file.

**5.5 The licence situation is the thing most likely to embarrass the project.** There is no `LICENSE` file anywhere in the tree. `README.md:249-251` says so and flags the Shaka issue, which is the right instinct, but the specifics are worse than the note suggests:

- **Shaka copy.** `apps/vega-player/src/w3cmedia/shakaplayer/ShakaPlayer.ts:1-13` is headed "AMAZON PROPRIETARY/CONFIDENTIAL … You may not use this file except in compliance with the terms and conditions set forth in the accompanying LICENSE.TXT file." No `LICENSE.TXT` accompanies it here. `dist/shaka-player.compiled.js` and the seven polyfills are also committed. The intent is to publish this repository as the Open Source mini-challenge entry. Copying a file marked confidential into a repository you plan to make public, without the licence it names, is the finding a judge will remember. Resolve it now: either get written confirmation from Amazon, or replace the wrapper with hls.js as the README itself suggests.
- **Roboto Flex.** Five TTFs at `apps/vega-player/assets/fonts/` with no OFL text. `docs/prior-art.md:57` says they came "from CI's download", and `docs/phase-reports.md:99` says they are static instances made with fontTools from the variable file. The SIL OFL requires the licence to travel with the fonts and with derived instances. Add `OFL.txt` and record where the original came from.
- **Caption with Intention.** `docs/prior-art.md:7` records that the design system PDF is "All Rights Reserved", that scratchpad copies were taken, and that the rules were adopted "verbatim" — including all 18 palette hex values (now in `theme.ts:20-31`) and the After Effects template's animation constants read out of the `.aep` (`prior-art.md:65-73`). `README.md:203` says "no assets from it are used here". Rules and colour values are thin copyright and the acknowledgement in `README.md:203` and the "not a clone of Caption With Intention" disclaimer at `:218` are the right posture, but the two sentences are in tension with `prior-art.md` and a reviewer will read both. The clean fix is a paragraph disclosing exactly what was taken (palette values, typographic rules, animation parameters, the typeface) plus an email to Chicago Hearing Society asking for acknowledgement or permission — CI's own page 50, quoted at `prior-art.md:63`, says they want this technology built, so the answer is likely to be yes and a written yes is worth a great deal in a submission.
- **Tears of Steel.** Attribution is present in `assets/tos-*/README.md` and in the app (`AboutScreen.tsx:19`), in Blender's requested form. CC BY 3.0 also requires indicating that the work was adapted; the excerpts are trimmed and re-encoded and the captions re-timed from the official SRT. Add "excerpt, re-encoded" to the on-screen credit.
- **Repository size.** `.git` is 150 MB, holding two committed film excerpts, three placeholder MP4s, five TTFs and a compiled Shaka bundle. If any of those has to be removed for licensing, it has to be removed from history, not just from `HEAD`.

**5.6 Other things a judge would notice.** `media/config.ts:17` commits a private LAN IP. `docs/device-log-2026-09-02-render-latency.txt` contains `'Error installing polyfill!', [TypeError: undefined is not a function]` on every run, unremarked in any document. `schema.ts:30-31` still declares `$id: ".../companion-profile-0.1.schema.json"` and `title: "… v0.1"` inside the constant, corrected only by the override in `tools/export-schema.ts:15`. The product is still called "Sightline" in the package id (`com.sightlinewip.player`), the storage key (`store.ts:13`), the npm scope and every document, with the rename listed as an unstarted external dependency five weeks before the internal freeze.
